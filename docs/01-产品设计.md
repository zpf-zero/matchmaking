## 一、产品定位

**严肃婚恋交友小程序**。核心价值 = **信息真实** + **条件匹配效率**。

与陌生人社交（探探/soul）的区别：
- 资料以**婚恋硬条件**为核心（学历、收入、房车、婚史），而非兴趣标签
- 资料需**人工审核**通过才进入推荐池，头像必须真人正脸
- 目标是**线下见面结婚**，不是线上聊天时长

**目标用户**：22-45 岁有明确结婚意愿的单身人群。

## 二、核心决策（已确认）

| 项 | 决策 |
|---|---|
| 撮合模式 | 自助匹配为主（用户自己浏览筛选，互相喜欢即配对），红娘功能留二期 |
| 商业模式 | 一期全免费，**不接微信支付**，数据表与接口预留付费位 |
| 登录方式 | 微信 `getPhoneNumber` 一键授权手机号 |
| 联系方式 | 站内 WebSocket 聊天，不直接暴露微信号 |
| 地理位置 | **一期不做 LBS「附近的人」**，只做按城市筛选。避免地理位置权限带来的审核风险 |
| 匹配性别 | **只推异性**，不支持同性匹配 |
| 性别修改 | **注册选定后锁死不可改**，防止刷池子 |
| 聊天次数 | **一期不限制条数**，二期做付费墙时再加限制 |
| 图片存储 | **一期存本地磁盘** `server/uploads`，不接对象存储 |
| 认证体系 | **一期不做**认证徽章（实名/学历/收入/房车），真实性靠资料人工审核 |
| 项目规模 | **小型项目**。9 张表、无缓存、无预计算、无独立管理后台 |
| 域名校验 | 开发阶段小程序开启「不校验合法域名」，直连 `http://localhost:8080` |

## 三、角色与权限

权限由**两个正交维度**共同决定：`status`（账号状态，管 C 端功能）与 `role`（角色，管管理功能）。

### 3.1 账号状态维度 `user.status`

| 状态 | 权限 |
|---|---|
| 游客（未登录） | 仅能看登录页 |
| 0 待完善 | 已登录，未填完资料 → **不能浏览他人**，强制引导完善 |
| 1 待审核 | 资料已提交 → 可浏览他人，但**自己不出现在他人列表中**，不能发起喜欢 |
| 2 正常 | C 端全部功能 |
| 3 已拒绝 | 同待审核，展示拒绝原因，可重新提交 |
| 4 已封禁 | 仅能看封禁提示页 |

**设计要点**：资料未完善不能浏览他人。这是婚恋产品的通行做法，防止只看不填的白嫖用户，保证资料池质量。

### 3.2 角色维度 `user.role`

**管理员不是独立账号体系**。管理员就是 `role > 1` 的普通用户记录，同样有 openid、同样用微信登录小程序，登录后「我的」页会多出管理入口。

| role | 名称 | 额外权限（向上包含） |
|---|---|---|
| 1 | 普通用户 | 无 |
| 2 | 审核员 | 资料审核（含照片）、举报处理、数据概览 |
| 3 | 管理员 | + 用户封禁/解封 |
| 4 | 超级管理员 | 同管理员（一期无独立超管功能，角色改配置文件/数据库） |

**两个维度互不干扰**：
- 管理员**不需要**填婚恋资料就能用管理功能（`role > 1` 跳过 status 拦截）
- 管理员**也可以**正常填资料参与相亲，一个账号两种身份不冲突
- 反过来，一个 `status=4 已封禁` 的用户即便 role 被误设，管理接口也会拒绝

### 3.3 首个超管如何产生

`config.dev.yaml` / `config.prod.yaml` 配置 openid 白名单，命中的用户登录时自动置为 `role=4`：

```yaml
admin:
  super_admin_openids:
    - "o1234567890abcdef"
```

解决「没有管理员就无法任命管理员」的死锁，且不必手改数据库。后续超管在小程序管理页面里给其他人升级角色即可。

## 四、状态机

### 4.1 用户状态 `user.status`

```
0 待完善  →（提交资料）→ 1 待审核 →（审核通过）→ 2 正常
                              ↓（审核拒绝）
                          3 已拒绝 →（重新提交）→ 1 待审核

任意状态 →（违规）→ 4 已封禁
```

### 4.2 资料审核 `user_profile.audit_status`

`0 待审核 / 1 通过 / 2 拒绝`，拒绝时必填 `audit_remark`，小程序端展示拒绝原因。

审核队列遵循以下规则：
- 新用户保存资料只是草稿，只有执行“提交审核”、用户状态变为 `status=1` 后才进入审核队列。
- 已审核用户修改资料或新增相册照片时，资料重新变为待审核，但用户在审核期间保持 `status=2`，可继续使用已开放功能。
- 审核队列只包含 `status=1` 的首次审核用户和 `status=2` 的复审用户，避免未完成注册的草稿被管理员提前通过。

### 4.3 配对流程

```
A 喜欢 B          → interaction(A→B, like)，B 收到「谁喜欢我」提醒
B 也喜欢 A        → 生成 conversation（配对即会话），双方收到「配对成功」
A pass B          → interaction(A→B, pass)，B 不再出现在 A 的推荐流
任一方拉黑/解除配对 → conversation 关闭，互不可见
```

### 5.2 首页设计

```
┌─────────────────────────────┐
│  为你推荐                     │
├─────────────────────────────┤
│  ┌───┐  张小姐 · 匹配 85%      │
│  │照 │  28岁 · 165cm · 本科    │  ← 条件卡片列表（非左右滑）
│  │片 │  杭州 · 未婚 · 产品经理 │
│  └───┘  3小时前活跃       [♡] │
├─────────────────────────────┤
│  ...                         │
└─────────────────────────────┘
```

**为什么用列表不用左右滑卡片**：婚恋用户需要对比硬条件，卡片流适合看脸的社交产品，列表适合看条件的婚恋产品。

### 5.3 管理端形态

**没有独立的 Web 管理后台**，管理功能内置在同一个小程序里。

**入口**：「我的」页面底部，`role > 1` 时才渲染「管理入口」菜单项。普通用户看不到该入口，直接输入路径也会被后端拦截。

```
我的
 ├─ 我的资料
 ├─ 择偶要求
 ├─ 我的喜欢
 ├─ 设置
 └─ ⚙️ 管理入口        ← 仅 role > 1 可见
      ├─ 数据概览        总用户 / 今日新增 / 待审核 / 配对数
      ├─ 资料审核 ⑤      角标显示待办数
      ├─ 举报处理 ①
      └─ 用户管理        搜索、封禁/解封（role>=3）
```

**为什么可行**：审核工作的核心是看照片和证件图，手机的显示效果和放大手势反而比 PC 更顺手；审核员可以随时随地处理，不用守着电脑。

**为什么安全**：前端隐藏入口**不是**安全措施，只是体验优化。真正的防线是后端——每个管理接口都挂 `RequireRole` 中间件，从 JWT 取出 user_id 后**回查数据库**校验实时 role，不信任 token 里的角色声明。

**取舍**：数据看板只做关键数字 + 简单趋势，不做复杂图表；用户管理以搜索定位为主，不做大表格多列排序。这些在手机上做体验差，且小型项目用不上。

最多 9 张，全部需审核。头像随资料一起审核；已通过用户新增照片时会自动进入复审队列，待审核照片不会展示给其他用户。

## 七、真实性保障

**一期只做一层：资料人工审核。**

用户正式提交资料后进入审核队列，审核员逐条核验昵称、自我介绍、头像、相册是否真实合规，通过后才进入推荐池。仅保存但尚未提交的草稿不进入队列。审核通过后修改资料或新增照片会触发复审，待审照片不会对外展示。头像必须真人正脸。

> **一期不做认证徽章体系**（实名/学历/收入/房产/车辆五种材料上传 + 审核 + 徽章 + 推荐加权）。这一整套的工作量接近小半个项目，而在用户基数小的初期，人工审核已经足够保证资料质量。等池子做起来、真实性成为瓶颈时再加，届时只需新增一张 `user_verify` 表，不影响现有结构。

也因此，一期**不涉及身份证等敏感证件的收集与存储**，合规风险和实现复杂度都低得多。

## 八、推荐排序算法（一期）

用 SQL + 内存计算实现，不引入推荐引擎。

**第一步 · 硬过滤**
```
性别 = 异性
status = 2（正常）
profile.audit_status = 1（审核通过）
排除：我已 like / 已 pass 的人
排除：黑名单双向
```

同时把**我的择偶要求**（年龄、身高、学历、收入、婚史、是否接受子女、期望城市）直接翻译成 SQL 条件，一并过滤。期望城市使用 `city_codes` 精确匹配。

**第二步 · 排序**

```sql
ORDER BY last_active_at DESC
```

就这一条。活跃用户优先展示，简单且效果不差。登录后的鉴权请求最多每 5 分钟更新一次 `last_active_at`，避免每次请求都写数据库。

**匹配度只展示、不排序**：结果返回后在 Go 里算一个双向匹配度百分比（我的要求命中对方 × 50% + 对方要求命中我 × 50%），显示成卡片上的「匹配度 85%」。用户看得见，但不参与排序。

> **一期不做加权打分和 rank_score 预计算**。原设计里“匹配度×50 + 认证分×20 + 活跃度×20 + 完整度×10”配套的统计表、缓存和复杂任务没有必要。分页仍使用普通 `LIMIT/OFFSET`；用户喜欢某人后前端重新拉取第一页，避免数据缩减导致下一页漏一条。年龄字段每天由服务端轻量任务刷新一次，不引入任务框架。

## 九、内容安全（必做）

婚恋类小程序是微信重点审核对象，以下为强制项：

1. **文本安全**：昵称、自我介绍、聊天消息 → 调用 `security.msgSecCheck`（免费）
   - 🕐 无 AppSecret 期间降级为**本地敏感词库**过滤，拿到凭证后切换
2. **图片安全**：头像、相册由管理端人工审核，待审核图片不对外展示；聊天图片可通过举报追溯处理
   - 🕐 AppID/AppSecret 到位后再补微信图片内容安全能力，当前不启用必须依赖真实凭证的接口
3. **举报入口**：他人资料页、聊天页必须有举报按钮
4. **拉黑**：拉黑后双向不可见
5. **一键注销**：设置页必须有账号注销入口（微信合规要求）
6. **协议**：《用户协议》《隐私政策》，登录页必须勾选同意
7. **未成年拦截**：生日计算 < 18 岁直接拒绝注册

## 十一、技术架构

```
        ┌─────────────────────────────┐
        │      uni-app 小程序          │
        │      Vue3 + TS + Pinia       │
        │  ┌───────────┬────────────┐  │
        │  │  C 端页面  │ 管理页面    │  │
        │  │  全部用户  │ role>1 可见 │  │
        │  └───────────┴────────────┘  │
        └──────────────┬───────────────┘
                       │ HTTPS / WSS
                       │ 同一套 JWT
                       ▼
        ┌──────────────────────────────┐
        │      Go 1.25 + Gin           │
        │  ┌────────────────────────┐  │
        │  │ Auth → Browse/Active  │  │
        │  │      → RequireRole     │  │
        │  └────────────────────────┘  │
        │  router → handler → service  │
        │              → gorm          │
        └───┬──────────────────┬───────┘
            ▼                  ▼
      ┌──────────┐      ┌──────────────┐
      │ MySQL 5.6+│      │ 本地磁盘存储  │
      │  (gorm)  │      │ uploads/     │
      └──────────┘      └──────────────┘
              一张 user 表，role 区分身份
```

**技术选型说明**

| 层 | 选型 | 理由 |
|---|---|---|
| 小程序 | uni-app + Vue3 + TS + Pinia | 已定，后续可一套代码出 H5/APP |
| UI | uni-app 原生组件 + 自定义样式 | 小项目减少依赖，保持页面轻量 |
| 管理端 | **无独立项目**，内置在小程序中 | 小型项目，一套代码一套登录，减少一半前端工作量 |
| 后端 | Go 1.25 + Gin + GORM v2 | 已定 |
| 数据库 | MySQL 5.6+ | 当前云库 5.6，建表脚本兼容 5.6~8.x |
| 存储 | 本地磁盘 `server/uploads` | 一个上传函数搞定，不做 Storage 接口抽象。二期要换 OSS 时再重构，成本一样低 |
| 缓存 | **不用** | 几百到几千用户，MySQL 直接扛得住。加缓存只会引入一致性问题 |
| 鉴权 | JWT（有效期 7 天），payload 带 role | C 端与管理端**同一套 token**，无需两套登录体系 |
| 长连接 | gorilla/websocket | 聊天。单机内存 hub，不做集群方案 |
| 日志 | zap | |
| 配置 | viper + 开发/生产 YAML | 前端构建前同样从 YAML 生成接口配置 |

**环境配置与构建**

- 后端默认读取 `server/config.dev.yaml`，可通过 `-c config.prod.yaml` 切换生产配置。
- 前端使用 `miniapp/config.dev.yaml` 与 `miniapp/config.prod.yaml` 保存接口地址。
- `npm run dev:mp-weixin` 构建前生成开发配置，`npm run build:mp-weixin` 构建前生成生产配置。
- 自动生成文件为 `miniapp/src/config.generated.ts`，业务代码不直接硬编码服务器地址。
- `miniapp/dist` 是构建输出，不纳入源码版本管理。

**目录结构**

```
matchmaking/
├── docs/                    设计文档
├── server/                  Go 后端
│   ├── cmd/main.go
│   ├── config.dev.yaml / config.prod.yaml
│   ├── internal/
│   │   ├── config/          配置加载
│   │   ├── model/           GORM 模型 + 枚举常量
│   │   ├── dto/             请求/响应结构
│   │   ├── service/         业务逻辑（直接用 gorm.DB）
│   │   ├── handler/         HTTP 处理（含 admin_*.go 管理端）
│   │   ├── middleware/      Auth / RequireBrowse / RequireActive / RequireRole / 日志 / CORS
│   │   ├── router/          路由注册
│   │   ├── ws/              WebSocket hub
│   │   └── pkg/             wechat / jwt / response / upload / sensitive
│   ├── migrations/          SQL 建表脚本
│   └── uploads/             图片存储
└── miniapp/                 uni-app 小程序（含管理页面）
    └── src/pages/
        ├── index/ search/ message/ mine/ ...   C 端页面
        └── admin/                               管理端页面
```

> **没有独立的 `admin/` 前端项目**。管理端是小程序内的一组页面，与 C 端共用请求封装、状态管理和 UI 组件库。

> **没有 repository 层**。原设计里 `handler → service → repository → model` 的四层，在小项目里 repository 就是一层纯转发的样板代码。改为 `handler → service → gorm`，service 里直接写查询。

> **uploads 不分 public/private**。一期不收集身份证等敏感材料，没有私有目录的需要，全部走 Gin 静态路由。

### 13.1 依赖 AppID/AppSecret 的功能与降级方案

真实微信登录、手机号和微信内容安全能力需要 AppID/AppSecret。登录、手机号和文本安全已经提供 Mock/真实双实现；图片内容安全暂不启用，凭证和正式域名到位后再接入。

| 功能 | 微信接口 | 无凭证时的降级实现 |
|---|---|---|
| 登录换 openid | `code2Session` | `wechat.mock=true` 时，把前端传来的 `code` 直接当作 mock openid 落库。开发者工具里可用不同 code 模拟多个账号 |
| 一键获取手机号 | `getPhoneNumber` | Mock 模式下前端弹输入框手填手机号，走同一个 `/auth/bind-phone` 接口。字段、流程、表结构完全一致 |
| 文本内容安全 | `msgSecCheck` | Mock 模式走**本地敏感词库**（内置词表文件）做兜底过滤，接口签名不变 |
| 图片内容安全 | 后续接入微信图片安全能力 | 当前头像与相册走人工审核，聊天图片依靠举报处理；不启用依赖真实凭证的接口 |
| 订阅消息推送 | `subscribeMessage.send` | 二期功能，一期不做 |

**关键点**：登录、手机号和文本安全封装在 `internal/pkg/wechat` 包里，对上层 service 暴露统一接口。Mock 与真实实现通过 YAML 开关切换；图片安全作为凭证到位后的独立补充项。

```yaml
# server/config.dev.yaml
wechat:
  mock: true          # ← 拿到凭证后改成 false
  app_id: ""          # ← 填入
  app_secret: ""      # ← 填入
```

**你后续需要给我的**：AppID、AppSecret 两个字符串即可，我改配置 + 验证真实登录流程。
