# 婚介小程序 · 接口设计 v1.3

开发 Base URL：由 `miniapp/config.dev.yaml` 生成，默认 `http://localhost:8080`
生产 Base URL：由 `miniapp/config.prod.yaml` 生成，域名申请完成后填写
统一前缀：`/api/v1` · 管理接口：`/api/v1/admin/*`

> **单一后端、单一登录、单一 token**。管理接口不是独立服务，只是挂了 `RequireRole` 中间件的一组路由。

> **v1.3 变更（权益体系重构）**：权益判定从 `vip_expire_at`（到期时间）改为 `vip_level`（永久等级）；新增三观问答（第八章）、原生家庭与行业标签（第九章）；照片分层（前 3 张免费）。设计与决策依据见 `docs/08-权益体系重构方案.md`。

## 统一响应

```json
{ "code": 0, "message": "ok", "data": {} }
```

| code | 含义 |
|---|---|
| 0 | 成功 |
| 400 | 参数错误 / 业务校验失败（`message` 为可直接展示给用户的文案） |
| 401 | 未登录 / token 失效 |
| 403 | 角色权限不足（`RequireRole` 拦截） |
| 404 | 资源不存在 |
| 4001 | 资料未完善（前端跳转填资料向导） |
| 4002 | 资料审核中 |
| 4003 | 资料审核未通过 |
| 4004 | 账号已封禁 |
| 500 | 服务器错误 |

**鉴权**：Header `Authorization: Bearer <token>`

**分页**：统一 `?page=1&page_size=20`，响应 `{ list: [], total: 0, page: 1, page_size: 20 }`

> 推荐流也用普通分页，不做游标分页。小数据量下翻页重复的概率可忽略，不值得为它引入游标 + 结果缓存。

## 一、认证 `/api/v1/auth`

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/wx-login` | 传 `code`，返回 `token` + `user` + `need_profile` | 否 |
| POST | `/sms/send` | H5 手机号登录：发送验证码（手机号/IP 限频；开发环境返回 `dev_code`） | 否 |
| POST | `/sms/login` | H5 手机号验证码登录；手机号不存在时自动建号 | 否 |
| POST | `/bind-phone` | 传微信 `code`（getPhoneNumber 回调），解密手机号；Mock 模式下直接传 `phone` 字段 | 是 |
| POST | `/logout` | 退出 | 是 |
| DELETE | `/account` | 注销账号（软删 + 匿名化） | 是 |

```
POST /wx-login
Req : { "code": "081xxx" }
Res : {
  "token": "eyJ...",
  "user": { "id": 1, "nickname": "...", "avatar": "...", ... },
  "status": 0,           // 账号状态，决定 C 端可用范围
  "role": 1,             // 角色，>1 时前端渲染管理入口
  "need_profile": true
}
```

> **管理员走的是同一个接口**。前端拿到 `role > 1` 就在「我的」页渲染管理入口，不需要单独的管理员登录页。

### H5 手机号验证码登录

H5 没有微信授权，手机号即账号。小程序端仍走 `/wx-login`，两端共用同一套 `token` 与账号状态。

```
POST /sms/send
Req : { "phone": "13800138000" }
Res : { "expires_in": 300, "resend_in": 60, "dev_code": "482913" }
      // dev_code 仅开发环境（server.mode != release 且 sms.mock=true）返回

POST /sms/login
Req : { "phone": "13800138000", "code": "482913" }
Res : 与 /wx-login 完全一致：token / user / status / role / need_profile
```

- **建号规则**：按手机号找账号，找不到才建号（`openid` 写 `h5_<手机号>` 占唯一索引）；微信账号已绑定同一手机号时，H5 登录到同一个账号。
- **验证码**：6 位、5 分钟有效、单码最多校验 5 次、用后即焚；服务端只存 HMAC-SHA256 哈希。
- **限频**：同手机号 60 秒冷却、24 小时最多 5 条；同 IP 每小时最多 20 条（`sms.*` 配置）。
- **账号边界**：H5 手机号账号与小程序微信账号暂不做自动合并。微信登录不会按手机号命中 H5 账号；微信账号绑定一个已被 H5 占用的手机号会被拒绝，需后续做账号绑定/合并。

```
POST /bind-phone
真实模式 Req : { "code": "getPhoneNumber 回调的 code" }
Mock 模式 Req : { "phone": "13800138000" }
Res : { "phone": "138****8000" }
```

> **Mock 模式**（`config.wechat.mock = true`，AppID/AppSecret 到位前的默认值）：
> - `/wx-login` 的 `code` 直接作为 mock openid 落库，不调微信 API。开发者工具中用不同 code 可模拟多个账号
> - `/bind-phone` 接受前端手填的 `phone`，不走微信解密
> - 两种模式共用同一套接口路径、表结构与前端流程，切换只改配置，前端按 `/common/config` 返回的 `mock_mode` 字段决定手机号是走授权按钮还是输入框

## 三、发现 `/api/v1/discover`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/recommend` | 推荐流（按活跃时间倒序，用年龄/身高/学历/收入/婚史/子女/期望城市过滤，返回双向匹配度） |
| GET | `/search` | 条件筛选 |

`/search` 查询参数：
```
age_min, age_max, height_min, height_max,
education_min, income_min, marital_status, has_children,
city_code, house_status, car_status, industry
```

> `industry` 是 v1.3 新增的行业标签筛选（「同系统」）。粗粒度到「教育系统 / 医疗卫生」一级，不含具体单位 —— 这是「熟人背书」的合规落点：给归属感，不给可识别到人的信息（见 `docs/08` 3.3）。

**推荐流排序（v1.3 起）**：`有效权益用户 → last_active_at DESC → id DESC`。

排序 SQL 在活跃时间之前插入权益加权，权益用户优先曝光：

```sql
ORDER BY (u.vip_level >= 1) DESC,
         u.last_active_at DESC, u.id DESC
```

> **v1.3 变更**：权益判定从 `vip_expire_at`（到期时间）改为 `vip_level`（永久等级）。原表达式依赖「有到期时间且未过期」，现在只判断等级 ≥ 1。用表达式而不是 JOIN 会员表，因为权益字段就存在 `user` 表上，不需要额外维护「是否会员」的冗余字段。该加权是权益「曝光加成」的唯一实现点，`/recommend` 与 `/search` 共用同一段排序逻辑。

## 四、互动 `/api/v1/interaction`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/like` | `{ to_user_id }` → 返回 `{ is_match: true/false, conversation_id }` |
| POST | `/pass` | 不喜欢 |
| DELETE | `/like/:to_user_id` | 取消喜欢 |
| GET | `/liked-me` | 谁喜欢我 |
| GET | `/my-likes` | 我喜欢谁 |
| GET | `/viewed-me` | 谁看过我（**返回结构与其他列表不同**，见下） |
| GET | `/unread-count` | 各类未读数（红点） |
| PUT | `/read?type=1或2` | 标记“谁看过我”或“谁喜欢我”为已读 |

### 「谁看过我」的权益门禁

接口本身**不做门禁**（非登录/未完善用户不会被拦），门禁体现在返回的数据量上 —— 非权益用户只拿到前 3 条，剩余人数通过 `locked` 告知：

```json
GET /api/v1/interaction/viewed-me?page=1
Res : {
  "list": [ { 用户卡片 } ],
  "total": 12,          // 实际看过我的人（已剔除封禁/拉黑/资料下架者）
  "locked": 9,          // 需权益解锁的人数，非权益用户 = total - free_limit
  "unlocked": false,    // 我是否已解锁完整资料（vip_level ≥ 1）
  "free_limit": 3       // 免费额度
}
```

> `page > 1` 时非权益用户返回空列表 —— 防止绕过第一页限制把剩余数据翻出来。`total` 与 `list` 用同一个 baseQuery **口径必须一致**，否则会出现「锁了但解不开」的幻影数字（对方封禁/拉黑/资料下架后不该再计入）。

## 五、配对与聊天

**配对即会话**。互相喜欢时直接创建 conversation，没有独立的 match 概念和接口。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/conversation/list` | 会话列表（= 配对列表） |
| DELETE | `/api/v1/conversation/:id` | 解除配对（关闭会话） |
| GET | `/api/v1/message/list` | `?conversation_id=&before_id=&limit=20` 历史消息 |
| POST | `/api/v1/message/send` | HTTP 兜底发送（WS 断开时） |
| PUT | `/api/v1/message/read` | 标记已读 |
| PUT | `/api/v1/message/recall` | `{ message_id }` 撤回消息，**仅限本人、发出 2 分钟内** |

### 消息撤回规则

- 服务端校验：只能撤自己的、2 分钟内的、非系统消息；前端长按超时的消息不显示撤回入口，但**以服务端校验为准**
- 撤回后原消息就地转为系统消息（`type=3`，`content="撤回了一条消息"`），前端按 `from_user_id` 显示「你/对方撤回了一条消息」
- 撤回的恰好是最后一条时，同步刷新会话列表摘要为 `[消息已撤回]`
- 通过 WS `recall` 事件实时通知对方

### WebSocket `/ws?token=<jwt>`

客户端 → 服务端：
```json
{ "type": "send",   "data": { "conversation_id": 1, "msg_type": 1, "content": "你好", "temp_id": "t1" } }
{ "type": "read",   "data": { "conversation_id": 1 } }
{ "type": "typing", "data": { "conversation_id": 1 } }
{ "type": "ping" }
```

服务端 → 客户端：
```json
{ "type": "message", "data": { 消息对象 } }
{ "type": "ack",     "data": { "temp_id": "t1", "message": { 消息对象 } } }
{ "type": "match",   "data": { "conversation_id": 1, "peer": { id, nickname, avatar } } }
{ "type": "like",    "data": { "id": 1, "nickname": "...", "avatar": "..." } }
{ "type": "typing",  "data": { "conversation_id": 1 } }
{ "type": "recall",  "data": { "conversation_id": 1, "message_id": 100, "from_user_id": 1 } }
{ "type": "unmatch", "data": { "conversation_id": 1 } }
{ "type": "pong" }
```

事件说明：

| 事件 | 触发 | 前端行为 |
|---|---|---|
| `typing` | 对方在输入框打字（客户端 3 秒节流上报，服务端只转发不落库） | 聊天页顶部显示「正在输入...」，4 秒无后续自动消失 |
| `recall` | 对方撤回消息 | 将本地对应消息就地转为系统提示 |
| `like` | 有人喜欢我 | **全局监听**（App.vue），任意页面弹 toast + 刷新红点 |
| `match` | 配对成功。**只推给被动方** —— 发起方已从 like 接口的 HTTP 响应拿到 `is_match`，重复推送会导致弹窗弹两次 | 全局弹「配对成功」弹窗，可直达聊天 |

心跳：客户端 25s 一次 ping，服务端 60s 无心跳断开。小程序端断线自动重连（指数退避，上限 30s）。发送消息后 10 秒未收到 `ack`，前端将消息标记为失败并提供点击重试；长连接未建立时直接使用 HTTP 发送接口兜底。

> WebSocket hub 用单机内存 map 维护连接，不做多实例广播方案。单机足够撑到几千并发。

### 图片上传（本地磁盘方案）

```
Req : multipart/form-data，字段 file，query ?scene=avatar
Res : { "url": "/uploads/photo/2026/08/03/a1b2c3d4.jpg", "path": "..." }
```

**磁盘目录规则**
```
server/uploads/            ← Gin 静态路由 /uploads 直接暴露
├── avatar/YYYY/MM/DD/
├── photo/YYYY/MM/DD/
├── chat/YYYY/MM/DD/
```

## 七、邀请裂变 `/api/v1/invite`

**定位**：合规版的「邀请有礼」。奖励发放的唯一触发点是**被邀请人通过人工审核**，不是注册、也不是分享动作本身。

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/my-code` | 我的邀请码、邀请进度、权益状态、邀请记录 | 是 |
| POST | `/bind` | `{ code }` 提交邀请码，建立邀请关系（**不发放权益**） | 是 |

```
GET /invite/my-code
Res : {
  "code": "K7M2XA",                    // 6 位邀请码，首次访问自动生成并持久化
  "invite_url": "/pages/login/index?invite=K7M2XA",
  "settled_count": 3,                  // 已结算人数
  "pending_count": 1,                  // 已绑定但被邀请人尚未通过审核
  "max_settle": 20,                    // 封顶人数
  "unlocked": true,                    // 我是否已解锁完整资料（永久，无到期时间）
  "records": [ { "nickname": "李*", "status": 1, "settled_at": "..." } ]
}
```

> **v1.3 变更**：不再返回 `reward_days` / `vip_expire_at` / `vip_active`，改为布尔 `unlocked`。权益从「限时天数」改为「永久解锁」，详见 `docs/08-权益体系重构方案.md` 4.4。前端因此不存在任何倒计时展示。

```
POST /invite/bind
Req : { "code": "K7M2XA" }
Res : { "code": 0, "message": "ok", "data": null }
```

### 状态机：绑定与结算刻意分离

```
被邀请人注册 ──［bind］──▶ invite_relation.status = 0 待达成
                                    │
                          填资料 + 提交审核
                                    │
              管理员 audit(pass=true) ──▶ status = 1 已结算 ──▶ 双方各永久解锁完整资料
```

**为什么奖励不挂在注册、也不挂在分享**：

1. 微信《运营规范》5.1.1 明文禁止「分享后解锁功能」、5.1.4 禁止「无深度互动即获利」。**「注册 + 完善资料 + 通过人工审核」是规范对深度互动的定义本身**，是本项目唯一能站住的形态。
2. 结算点越靠后，刷量成本越高：空号、资料不全、审核被拒的号一律拿不到奖励。合规要求与防刷需求在同一个设计上收敛。
3. 微信自 2024-07-05 起已砍掉分享完成回调（不再返回 `shareTicket`），「检测分享成功即发奖」技术路线已不可行，本方案不依赖任何分享回调。

### 防刷规则

| 规则 | 实现 |
|---|---|
| 一个被邀请人只能绑一次 | `invite_relation.uk_invitee` 唯一索引；并发重复提交按幂等返回 |
| 单邀请人封顶 | `settled_count >= 20` 时拒绝新绑定（**只计已结算**，待达成的不占额度） |
| 邀请人须状态正常 | 邀请人被 `status=4` 封禁时拒绝绑定，已绑定未结算的关系置为 `2 已作废` |
| 不能自邀 | `owner.user_id == me.id` 直接拒绝 |
| 权益幂等 | 重复调用审核不重复发放；已是解锁状态时不再写库 |

> **封禁只阻止新增、不追回已有权益**。邀请人在封禁前已合法达成的结算保持有效，否则一次误封就会抹掉用户已获得的权益。

### 权益设计模式（v1.3：永久等级制）

权益不用独立会员表，只存等级字段 `user.vip_level`：

```go
const (
    VipLevelNone     = 0 // 无权益
    VipLevelUnlocked = 1 // 已解锁完整资料（永久）
)

func (u *User) HasVip() bool {
    return u.VipLevel >= VipLevelUnlocked
}
```

> 旧的 `vip_expire_at` 字段保留不删（兼容历史数据与既有代码路径），但读取一律以 `vip_level` 为准，且该字段已标 `json:"-"` 不再对外返回。

一期权益范围五项，全部是「信息可见性」，不含任何行为限制：

| 权益 | 落点 |
|---|---|
| 更多照片（第 4 张起） | `/user/detail` 的 `locked_photo_count` / `photos_locked` |
| 三观问答答案 | `/user/detail` 的 `three_view` |
| 对方授权公开的原生家庭 | `/user/detail` 的 `family` / `viewed_family` |
| 谁看过我（全量 vs 免费 3 条） | `/interaction/viewed-me` 的 `locked` 字段 |
| 曝光加成（推荐流置顶） | `/discover/*` 的 ORDER BY 加权 |

> **为什么不抄竞品的「行为限制型」权益**（无限喜欢、每日 3 次）：珍爱/佳缘的权益卖给「急着结婚的人」，可做稀缺；我们的权益送给被邀请来的用户，目的是留存与资料质量。照搬行为限制会让本来就在犹豫的用户直接流失（见 `docs/08` 第八章）。
>
> **为什么改成永久而不是更长天数**：赠送权益用天数没有心理锚点（用户看到「剩 7 天」不知道能换来什么），倒计时还会加速犹豫型用户流失。防刷靠「被邀请人须通过人工审核」这一成本闸门，而不是靠时间衰减。

### 结算失败的降级

`SettleInvite` 由 `AuditUser` 在**事务提交成功后**调用，且**失败只记日志、返回 nil** —— 审核是业务主线，权益发放是附加动作，不能因为发权益出错导致管理员审不了资料。

### 合规配套（必须有，缺一不可）

| 项 | 位置 |
|---|---|
| 活动规则页 | `pages/invite/rules`，七节，字号与正文同级（不做视觉降级隐藏） |
| 规则页明确声明 | 「分享不是获得奖励的前提条件」（对齐 5.1.4） |
| 规则页隐私说明 | 原生家庭默认不对外展示、需主动授权；三观答案查看需权益 |
| 分享文案 | `onShareAppMessage` 只写自然语，不含「得奖励/解锁/领取」 |
| 禁止项 | 无 `shareTickets`/`getShareInfo` 调用，无红点/形变暗示分享，`enableShareTimeline: false` |

## 八、三观问答 `/api/v1/user/three-view`

**定位**：答题免费、**看答案**才需权益。三观是提高资料质量的核心抓手 —— 它不增加平台的数据采集成本，用户自己会产出内容（见 `docs/08` 4.2②）。

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/api/v1/common/three-view/questions` | 题库（题目 + 选项），无隐私，登录即可取 | 否 |
| GET | `/api/v1/user/three-view` | 我的答题状态与答案 | 是 |
| PUT | `/api/v1/user/three-view` | `{ answers: number[] }` 全量覆盖我的答案 | 是 |

```
PUT /api/v1/user/three-view
Req : { "answers": [0, 2, -1, 3, ...] }   // 与题库同序；-1 表示未答（可中途保存）
Res : { "code": 0, "message": "ok", "data": null }
```

**答案数组的下标契约**：`answers[i]` 对应题库第 `i` 题的选项下标，长度必须等于题库题数。任一非 `-1` 的下标越界则整体拒绝，避免写入半截脏数据。

**幂等实现**：按 `(user_id, q_id)` 唯一索引 upsert，不做「先删后插」—— 中途保存时那样会短暂清空历史，用户看到自己答案消失会很慌。

**展示侧（`/user/detail` 返回）**：

```json
"three_view": {
  "answers":    [0, 2, 3, 1, 0, 2, 1, -1],  // 对方答案；未解锁时为空
  "my_answers": [0, 2, 1, 1, 0, 3, 1, 0],   // 我的答案，便于前端并列渲染
  "answered": 7, "total": 8,
  "match_rate": 75,                          // 仅统计「双方都答过」的题
  "my_answered": true
},
"three_view_answered": true,   // 对方是否答过题（公开信息）
"three_view_unlocked": false   // 我是否有权限看对方答案
```

> **未解锁时 `three_view` 仍会返回 `answered` / `total`**，让免费用户看到「TA 答了 7 题，解锁后可查看」的明确预期，而不是一片空白（空白会被误读成「对方没填」）。
>
> **一致率只在双方都答过的题目上计算**，未答不参与。否则会鼓励用户为凑数乱答。

## 九、原生家庭与行业标签

### 行业标签（免费）

`user_profile.industry`，粗粒度枚举（机关事业单位 / 教育系统 / 医疗卫生 / 公检法 / 国有企业 / 金融银行 / 互联网·IT / 其他企业 / 自由职业 / 其他）。

用于 `/discover/search` 的「同系统」筛选与卡片展示。

> **只到「系统」级，不到具体单位**。写「教育系统」是归属感，写「XX市第三中学」就是可被反查到人。体制内用户对可识别信息极度敏感，这是「熟人背书」而非「熟人发现」的落点（见 `docs/08` 3.3）。

### 原生家庭（权益内容，默认私有）

`user_profile` 六个字段：`family_parent_occ` / `family_atmosphere` / `family_only_child` / `family_city` / `family_note` / `family_visible`。

**双重门禁**：只有「对方 `family_visible=1`（主动授权）」**且**「我已解锁（`vip_level≥1`）」时，`/user/detail` 才返回 `family` 对象。

> **默认私有是刻意设计**：这是敏感度最高的资料块，默认公开会劝退大量用户，尤其是一期以体制内为主的用户群（见 `docs/08` 6-2）。
>
> **「授权了但内容全空」不允许发生**：保存时不通过校验就强制把 `family_visible` 置 0 —— 那不叫公开，叫让人白点一下。
>
> **父母职业用「类型」不用「具体单位」**：写「公务员」可以，写「XX局」不行，后者结合年龄/城市可被反查到具体的人。
>
> 相关字段属于个人信息，须同步更新 `pages/common/agreement.vue` 与微信隐私保护指引（见 `docs/07` 第 6 项）。

## 八、管理接口 `/api/v1/admin`

**没有独立的管理员登录接口**。管理员用 `/api/v1/auth/wx-login` 微信登录，拿到的 token 与普通用户完全一致，区别只在 `role` 字段。

每个管理接口在路由注册时声明最低角色，由 `RequireRole(n)` 中间件统一校验。下表 **role** 列即该接口要求的最低角色。

全部 9 个接口：

| 方法 | 路径 | role | 说明 |
|---|---|---|---|
| GET | `/overview` | 2 | 总用户 / 今日新增 / 待审核数 / 配对数（实时 count） |
| GET | `/audit/list` | 2 | 待审资料/照片复审队列；仅包含 `user.status IN (1,2)`，不包含未提交草稿 |
| POST | `/audit/:user_id` | 2 | `{ pass: true/false, remark }`，同时处理资料与照片 |
| GET | `/report/list` | 2 | 举报列表 |
| POST | `/report/:id/handle` | 2 | `{ action: ignore/ban, remark }`，`ban` 需 role>=3 |
| GET | `/user/list` | 2 | 用户搜索 + 分页 |
| GET | `/user/:id` | 2 | 用户详情（全部资料 + 举报记录） |
| POST | `/user/:id/ban` | 3 | 封禁 `{ reason }` |
| POST | `/user/:id/unban` | 3 | 解封 |

**去掉的管理接口**：趋势图、字典 CRUD、系统配置 CRUD、角色管理、操作日志、风险消息、反馈列表。

- **角色怎么改**：`config.dev.yaml` / `config.prod.yaml` 白名单给超管，其他管理员直接 `UPDATE user SET role=2 WHERE id=?`。小项目里管理员就那么一两个人，为它做一套界面不值
- **资料与照片审核合并**：`/audit/list` 一次返回用户资料 + 头像 + 相册，审核员一屏看完一次性通过或拒绝，不用在两个队列间切换
- **草稿不进入队列**：新用户只有调用 `/user/submit-audit` 后才进入首次审核；已通过用户修改资料或新增照片时以 `status=2` 身份进入复审
- **审核通过是邀请结算的唯一触发点**：`AuditUser` 在事务提交成功且 `pass=true` 时调用 `SettleInvite(userID)`（见第七章）

## 九、中间件链

**同一套后端、同一套 Auth**。Auth 解析 JWT 后立即回查用户表，将完整用户放入 context，并统一处理封禁和活跃时间：

```
Recovery → Logger（token 脱敏）→ CORS
                                  │
登录资料路由 → Auth ──────────────┤
浏览路由     → Auth → RequireBrowse
互动聊天路由 → Auth → RequireActive
管理路由     → Auth → RequireRole(n)
```

**路由归组速查**

| 分组 | 中间件 | 包含 |
|---|---|---|
| `authed` | `Auth` | 填资料、上传、注销、**邀请码绑定（`/invite/*`）** |
| `browse` | `Auth + RequireBrowse` | 推荐、搜索、他人资料、三个互动列表 |
| `active` | `Auth + RequireActive` | like/pass、会话、消息、WS |
| `auditor` / `admin` / `superAdmin` | `Auth + RequireRole(2/3/4)` | 管理接口 |

> **`/invite/*` 刻意放在 `authed` 组**：绑定邀请码发生在「注册后、提交审核前」，此时用户 `status=0`，挂 `RequireBrowse` 会被 `4001` 拦掉，整个邀请流程就走不通。同理，举报/拉黑也放在 `authed` —— 被拒审用户也应当能举报违规者。

### Auth 中间件

- 解析 token 获取 `user_id`，随后按主键回查数据库。
- 权限与状态全部使用数据库实时值，不信任 token 中的 role/status。
- 封禁账号统一返回 `4004`。
- 距上次活跃超过 5 分钟时更新 `last_active_at`。
- WebSocket token 来自 query 参数，请求日志会将 `token` 替换为 `***`。

### RequireBrowse / RequireActive
按账号状态拦截，避免每个 handler 重复判断：

| status | 行为 |
|---|---|
| 0 待完善 | 只放行资料填写、上传、字典、配置类接口，其余返回 `4001` |
| 1 待审核 / 3 已拒绝 | 放行浏览类，拦截互动类（like/message），返回 `4002` / `4003` |
| 2 正常 | 全放行 |
| 4 已封禁 | 全拦截，返回 `4004` |

### RequireRole(n) 中间件（管理路由）

这是管理接口的唯一角色授权判定点，Auth 已提前完成用户查询和封禁判断：

```go
func RequireRole(min int) gin.HandlerFunc {
    return func(c *gin.Context) {
        u := middleware.CurrentUser(c)

        // Auth 已完成实时回查与封禁判断
        // 角色向上包含：role >= min 即通过
        if u.Role < min { abort(403); return }
        c.Next()
    }
}
```

**为什么必须回查数据库**：JWT 有效期 7 天，若某人被降级或封禁，旧 token 里的 `role` 仍是旧值。Auth 每次请求回查一次主键，RequireRole 直接复用 context 中的实时用户，不再重复查库。

**为什么不用前端隐藏入口做防护**：`role > 1` 才渲染管理菜单只是体验优化。用户完全可以直接构造请求打管理接口，拦不拦得住只取决于后端。

> **不做 AdminLog 中间件**，也不做 `admin_log` 表。管理员就一两个人，操作日志没人会去看。

> **不做 RateLimit**。一期用户量小，Gin 本身扛得住；真被刷了再加也是几行代码的事。
