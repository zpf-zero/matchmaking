# 婚介小程序 · 接口设计 v1.0

Base URL：`http://localhost:8080`
统一前缀：`/api/v1` · 管理接口：`/api/v1/admin/*`

> **单一后端、单一登录、单一 token**。管理接口不是独立服务，只是挂了 `RequireRole` 中间件的一组路由。

## 统一响应

```json
{ "code": 0, "message": "ok", "data": {} }
```

| code | 含义 |
|---|---|
| 0 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录 / token 失效 |
| 403 | 角色权限不足（`RequireRole` 拦截） |
| 404 | 资源不存在 |
| 4001 | 资料未完善（前端跳转填资料向导） |
| 4002 | 资料审核中 |
| 4003 | 资料审核未通过 |
| 4004 | 账号已封禁 |
| 500 | 服务器错误 |

**鉴权**：Header `Authorization: Bearer <token>`

**分页**：统一 `?page=1&page_size=20`，响应 `{ list: [], total: 0, page: 1, page_size: 20 }`

> 推荐流也用普通分页，不做游标分页。小数据量下翻页重复的概率可忽略，不值得为它引入游标 + 结果缓存。

## 一、认证 `/api/v1/auth`

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/wx-login` | 传 `code`，返回 `token` + `user` + `need_profile` | 否 |
| POST | `/bind-phone` | 传微信 `code`（getPhoneNumber 回调），解密手机号；Mock 模式下直接传 `phone` 字段 | 是 |
| POST | `/logout` | 退出 | 是 |
| DELETE | `/account` | 注销账号（软删 + 匿名化） | 是 |

```
POST /wx-login
Req : { "code": "081xxx" }
Res : {
  "token": "eyJ...",
  "user": { "id": 1, "nickname": "...", "avatar": "...", ... },
  "status": 0,           // 账号状态，决定 C 端可用范围
  "role": 1,             // 角色，>1 时前端渲染管理入口
  "need_profile": true
}
```

> **管理员走的是同一个接口**。前端拿到 `role > 1` 就在「我的」页渲染管理入口，不需要单独的管理员登录页。

```
POST /bind-phone
真实模式 Req : { "code": "getPhoneNumber 回调的 code" }
Mock 模式 Req : { "phone": "13800138000" }
Res : { "phone": "138****8000" }
```

> **Mock 模式**（`config.wechat.mock = true`，AppID/AppSecret 到位前的默认值）：
> - `/wx-login` 的 `code` 直接作为 mock openid 落库，不调微信 API。开发者工具中用不同 code 可模拟多个账号
> - `/bind-phone` 接受前端手填的 `phone`，不走微信解密
> - 两种模式共用同一套接口路径、表结构与前端流程，切换只改配置，前端按 `/common/config` 返回的 `mock_mode` 字段决定手机号是走授权按钮还是输入框

## 五、配对与聊天

**配对即会话**。互相喜欢时直接创建 conversation，没有独立的 match 概念和接口。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/conversation/list` | 会话列表（= 配对列表） |
| DELETE | `/api/v1/conversation/:id` | 解除配对（关闭会话） |
| GET | `/api/v1/message/list` | `?conversation_id=&before_id=&limit=20` 历史消息 |
| POST | `/api/v1/message/send` | HTTP 兜底发送（WS 断开时） |
| PUT | `/api/v1/message/read` | 标记已读 |

### WebSocket `/ws?token=<jwt>`

客户端 → 服务端：
```json
{ "type": "send",  "data": { "conversation_id": 1, "msg_type": 1, "content": "你好" } }
{ "type": "read",  "data": { "conversation_id": 1 } }
{ "type": "ping" }
```

服务端 → 客户端：
```json
{ "type": "message", "data": { 消息对象 } }
{ "type": "ack",     "data": { "temp_id": "x", "message_id": 100 } }
{ "type": "match",   "data": { 配对成功通知 } }
{ "type": "like",    "data": { 有人喜欢我 } }
{ "type": "pong" }
```

心跳：客户端 25s 一次 ping，服务端 60s 无心跳断开。小程序端断线自动重连（指数退避，上限 30s）。

> WebSocket hub 用单机内存 map 维护连接，不做多实例广播方案。单机足够撑到几千并发。

### 图片上传（本地磁盘方案）

```
Req : multipart/form-data，字段 file，query ?scene=avatar
Res : { "url": "/uploads/photo/2026/08/03/a1b2c3d4.jpg", "path": "..." }
```

**磁盘目录规则**
```
server/uploads/            ← Gin 静态路由 /uploads 直接暴露
├── avatar/YYYY/MM/DD/
├── photo/YYYY/MM/DD/
├── chat/YYYY/MM/DD/
└── report/YYYY/MM/DD/
```

- 文件名用 UUID，防止遍历与覆盖
- 限制：单张 ≤ 5MB，仅 jpg/jpeg/png/webp，按 magic number 校验真实类型而非扩展名
- **不分 public/private**：一期不收集身份证等敏感证件，全部图片都是可公开访问的头像/相册/聊天图
- 就是一个 `SaveImage(file, scene)` 函数，不做 `Storage` 接口抽象

## 八、管理接口 `/api/v1/admin`

**没有独立的管理员登录接口**。管理员用 `/api/v1/auth/wx-login` 微信登录，拿到的 token 与普通用户完全一致，区别只在 `role` 字段。

每个管理接口在路由注册时声明最低角色，由 `RequireRole(n)` 中间件统一校验。下表 **role** 列即该接口要求的最低角色。

全部 9 个接口：

| 方法 | 路径 | role | 说明 |
|---|---|---|---|
| GET | `/overview` | 2 | 总用户 / 今日新增 / 待审核数 / 配对数（实时 count） |
| GET | `/audit/list` | 2 | 待审资料队列（含该用户的头像和相册，一次返回） |
| POST | `/audit/:user_id` | 2 | `{ pass: true/false, remark }`，同时处理资料与照片 |
| GET | `/report/list` | 2 | 举报列表 |
| POST | `/report/:id/handle` | 2 | `{ action: ignore/ban, remark }`，`ban` 需 role>=3 |
| GET | `/user/list` | 2 | 用户搜索 + 分页 |
| GET | `/user/:id` | 2 | 用户详情（全部资料 + 举报记录） |
| POST | `/user/:id/ban` | 3 | 封禁 `{ reason }` |
| POST | `/user/:id/unban` | 3 | 解封 |

**去掉的管理接口**：趋势图、字典 CRUD、系统配置 CRUD、角色管理、操作日志、风险消息、反馈列表。

- **角色怎么改**：`config.yaml` 白名单给超管，其他管理员直接 `UPDATE user SET role=2 WHERE id=?`。小项目里管理员就那么一两个人，为它做一套界面不值
- **资料与照片审核合并**：`/audit/list` 一次返回用户资料 + 头像 + 相册，审核员一屏看完一次性通过或拒绝，不用在两个队列间切换

## 七、中间件链

**同一套后端、同一条基础链**，管理路由只是多挂一个中间件：

```
公共前段:  Recovery → Logger → CORS → JWT
                                       │
C 端路由   ────────────────────────────┼──→ UserStatus → Handler
                                       │
管理路由   ────────────────────────────┴──→ RequireRole(n) → Handler
```

### JWT 中间件
解析 token，取出 `user_id` 与 `role` 写入 context。**token 里的 role 仅作提示，不作为授权依据**。

### UserStatus 中间件（仅 C 端路由）
按账号状态拦截，避免每个 handler 重复判断：

| status | 行为 |
|---|---|
| 0 待完善 | 只放行资料填写、上传、字典、配置类接口，其余返回 `4001` |
| 1 待审核 / 3 已拒绝 | 放行浏览类，拦截互动类（like/message），返回 `4002` / `4003` |
| 2 正常 | 全放行 |
| 4 已封禁 | 全拦截，返回 `4004` |

### RequireRole(n) 中间件（仅管理路由）

这是**唯一的授权判定点**，逻辑固定四步：

```go
func RequireRole(min int) gin.HandlerFunc {
    return func(c *gin.Context) {
        uid := c.GetUint64("user_id")

        // 1. 回查数据库拿实时 role，不信任 token 里的声明
        var u model.User
        if err := db.First(&u, uid).Error; err != nil { abort(401); return }

        // 2. 封禁用户即便有 role 也一律拒绝
        if u.Status == StatusBanned { abort(403); return }

        // 3. 角色向上包含：role >= min 即通过
        if u.Role < min { abort(403); return }

        c.Set("role", u.Role)
        c.Next()
    }
}
```

**为什么必须回查数据库**：JWT 有效期 7 天，若某人被降级或封禁，旧 token 里的 `role` 仍是旧值。只信 token 会留出最长 7 天的越权窗口。回查是一次主键查询，成本可忽略；用户量上来后加一层短 TTL 缓存即可。

**为什么不用前端隐藏入口做防护**：`role > 1` 才渲染管理菜单只是体验优化。用户完全可以直接构造请求打管理接口，拦不拦得住只取决于后端。

> **不做 AdminLog 中间件**，也不做 `admin_log` 表。管理员就一两个人，操作日志没人会去看。

> **不做 RateLimit**。一期用户量小，Gin 本身扛得住；真被刷了再加也是几行代码的事。
