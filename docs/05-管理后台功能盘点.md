# 管理后台功能盘点与改造建议

> 盘点时间：2026-10-15
> 范围：H5 端管理后台（`miniapp/src/pages/admin/*` + `server/internal/service/admin.go` + `server/internal/router/router.go`）

---

## 一、结论先行

当前管理后台是一个**最小可用版本**：能审资料、能处理举报、能封禁用户，共 **5 个页面 / 9 个接口**。

但在三个层面上有明显欠缺：

1. **入口链路错位** —— 管理员登录后走的是「普通用户」路径（首页 → 我的 → 管理中心），新增管理员还会被**强制要求填写择偶资料**，与「管理员不需要填信息」直接冲突。
2. **运营能力缺失** —— 没有角色任命、没有审计日志、没有敏感词维护、没有数据报表、没有公告下发，运营侧几乎是「只能看不能管」。
3. **形态不匹配** —— 后台是纯移动端窄屏布局，管理员在电脑上操作时只能看到一条手机宽的界面（H5 在 ≥541px 只做了加边框 + 540px 居中）。

---

## 二、现状盘点

### 2.1 管理员登录链路（**问题最集中**）

**没有独立的管理员登录入口**，管理员与普通用户共用一套 `wx-login`：

| 环节 | 现状 | 问题 |
|---|---|---|
| 登录接口 | `POST /api/v1/auth/wx-login`（`service/auth.go:23`）| 管理员与普通用户完全同路径，靠 `role` 字段区分 |
| 超管自举 | `config.admin.super_admin_openids` 白名单命中即提 `role=4`（`auth.go:50`）| 只能启动第一个管理员，之后**无法通过界面任命**其他人 |
| 登录后跳转 | `login/index.vue:39`：`if (res.need_profile \|\| status === 0)` → 跳 `profile/setup`，否则跳**用户首页** | ① 新管理员（status=0）被强制去填择偶资料；② 管理员登录后进的是推荐流，不是后台 |
| 全局守卫 | `App.vue:57`：`if (store.status === 0)` → `reLaunch('profile/setup')` | 同上，加深了「管理员也要填资料」的错误路径 |
| 后台入口 | 只有「我的」页 `mine/index.vue:157` 的 `v-if="store.isAdminRole"` 菜单项 | 藏得深，每次都要手动导航；没有独立的 tab 或首页 |

**结论**：管理员登录链路需要重做。核心三点——① 管理员免填资料；② 登录后直接进后台；③ 后台应能独立访问（不依赖先逛用户端）。

### 2.2 现有后台功能清单

| 页面 | 路径 | 能力 |
|---|---|---|
| 工作台 | `admin/index` | 待审数、待举报数、6 个概览数字（注册/今日新增/7日活跃/配对数）、用户管理入口 |
| 资料审核 | `admin/audit` | 待审列表（资料+头像+相册一屏）；通过；拒绝（5 个预设原因 + 自定义） |
| 举报处理 | `admin/report` | 举报列表（含证据图）；忽略；封禁被举报人 |
| 用户列表 | `admin/user` | 关键词搜索（昵称/手机/ID）；状态筛选（待审/正常/未通过/已封禁）；分页 |
| 用户详情 | `admin/user-detail` | 资料、相册、被举报记录、喜欢/被喜欢/配对数；封禁/解封 |

接口共 9 个（`router.go:99-114`）：

```
审核员组（role ≥ 2）：overview / audit/list / audit/:id / user/list / user/:id / report/list / report/:id/handle
管理员组（role ≥ 3）：user/:id/ban / user/:id/unban
```

### 2.3 权限模型

```
RoleUser=1  普通用户
RoleAuditor=2  审核员   —— 审核资料、处理举报、看用户
RoleAdmin=3    管理员   —— 额外：封禁/解封
RoleSuperAdmin=4 超管   —— 目前无独有能力（白名单自举产生）
```

**问题**：`RoleSuperAdmin` 是个空壳，没有任何「只有超管能做」的操作（比如任命管理员），导致超管与管理员能力无异。

## 三、缺口清单（按模块 + 优先级）

### P0 — 直接影响「管理员进后台」这一诉求

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **管理员登录分流** | `role > RoleUser` 登录后直接 `reLaunch` 到 `/pages/admin/index`，不进用户首页 |
| 2 | **管理员免填资料** | 链路里的 `status === 0 → profile/setup` 需要对管理员豁免（用 `role` 判断，而非 `status`） |
| 3 | **新管理员初始状态** | 任命为管理员时自动把 `status` 置为正常，避免卡在「待完善资料」 |
| 4 | **角色任命接口** | 后台没有改 `role` 的接口（`handler/admin.go` 里完全没有 SetRole）。现在只能靠改数据库或白名单 |
| 5 | **后台独立导航** | 5 个页面靠 `navigateTo` 逐个进，没有统一的后台布局/侧边导航/返回后台首页的快捷方式 |

### P1 — 合规与风控刚需（婚恋品类尤其需要）

| # | 缺口 | 说明 |
|---|---|---|
| 6 | **操作审计日志** | 全库**没有** admin_log / operation_log 表。谁封了谁、谁驳回了什么，只写进 logger 文件，**不可查询、不可追溯**。婚恋平台一旦出纠纷（如误封、审核争议），没有证据链 |
| 7 | **处置手段阶梯** | 现在只有「忽略」和「封禁」两个极端。缺：警告、限制功能（禁言/禁止喜欢）、下架单张照片、限时封禁 |
| 8 | **相册单独处置** | 相册只能随资料整批过审（`admin.go:154`），不能单独下架某张违规照片 |
| 9 | **敏感词后台维护** | 词库是 `server/configs/sensitive_words.txt` 静态文件（`pkg/sensitive/sensitive.go`），改词要改文件 + 重启，**不能后台增删改查** |
| 10 | **内容机器审核** | 目前文本走本地敏感词 + 微信 `msgSecCheck`，但**图片没有任何机器审核**，全靠审核员肉眼 |

### P2 — 运营效率

| # | 缺口 | 说明 |
|---|---|---|
| 11 | **数据趋势与报表** | 工作台只有 6 个静态数字，无趋势图、无留存、无转化漏斗（注册→填资料→过审→配对→聊天）、无导出 |
| 12 | **批量操作** | 审核、封禁只能一个个点，无批量通过/批量封禁 |
| 13 | **公告 / 系统通知下发** | 消息模型里已有 `MsgSystem` 类型（`enum.go:58`），但**没有任何下发入口**，无法给全站或指定用户发通知 |
| 14 | **用户列表筛选维度** | 只能按 `status` 筛。缺：按角色、注册时间段、活跃时间、完成度、是否绑定手机筛选 |
| 15 | **举报处置记录** | 举报处理完没有留痕展示（`AdminReportList` 不含处理人和处理时间） |

### P3 — 体验与扩展

| # | 缺口 | 说明 |
|---|---|---|
| 16 | **桌面端后台布局** | H5 在 ≥541px 仅做「加边框 + 540px 居中」（`App.vue:243`），仍是手机窄条。后台应为宽屏双栏/侧边栏布局 |
| 17 | **用户反馈 / 工单** | 用户端只有「举报」，没有反馈入口；后台也没有工单处理 |
| 18 | **系统配置开关** | 无：注册开关、维护模式、审核强度、推荐参数（年龄/身高容差目前是 `discover.go` 里的常量） |
| 19 | **字典管理** | 学历/收入/婚况等字典硬编码在 `enum.go:77`，不能后台维护 |
| 20 | **登录日志 / 风控** | 无异地登录提醒、无多账号同设备识别、无异常行为（短时间大量喜欢/群发）监控 |
| 21 | **管理员查看会话** | 合规场景（配合公安/监管取证）需要，但必须严格权限 + 审计留痕，当前完全没有 |

## 四、建议的改造路线

### 第一批：把「管理员进后台」这条主线打通（P0）

1. **登录分流**（前端 2 处 + 后端 1 处）
   - `login/index.vue`：`role > 1` → 跳 `/pages/admin/index`，且跳过 `profile/setup`
   - `App.vue onLaunch`：`status === 0 && role <= 1` 才跳 `profile/setup`
   - 后端 `WxLogin`：管理员账号不返回 `need_profile`

2. **角色任命**（后端新增）
   - 新增 `POST /admin/user/:id/role`（仅超管可调），支持设为审核员/管理员/降回普通用户
   - 封禁/任命的约束已有雏形（`admin.go:259` 的「不能封禁同级或更高权限」），角色变更沿用同一套层级校验

3. **后台独立布局**（前端重构）
   - 把 `admin/*` 从「普通页面」提升为有统一外壳的后台：顶部/侧边导航 + 各功能页
   - H5 宽屏下用双栏（侧边菜单 + 内容区），窄屏自动折叠

### 第二批：补齐合规底线（P1）

4. 建 `admin_log` 表，所有管理动作（审核/封禁/角色变更/举报处置）写一条结构化记录，后台可查
5. 处置手段扩展为阶梯：忽略 → 警告 → 限制功能 → 限时封禁 → 永久封禁
6. 敏感词后台 CRUD + 热更新（去掉静态文件依赖）
7. 相册单张处置

### 第三批：运营能力（P2）

8. 数据报表：注册/活跃/配对的趋势曲线 + 转化漏斗 + CSV 导出
9. 批量审核 / 批量封禁
10. 系统公告下发

### 第四批：体验与扩展（P3）

11. 桌面端后台布局打磨
12. 用户反馈工单
13. 系统配置开关、字典管理

## 五、现状 → 目标 对照

| 维度 | 现状 | 目标 |
|---|---|---|
| 登录后落地页 | 用户首页（管理员也一样） | 管理员 → 后台工作台 |
| 填资料 | 所有 status=0 的账号都要填 | 管理员豁免 |
| 角色任命 | 只能改数据库 / 白名单 | 超管在后台任命 |
| 审计追溯 | 无（只有日志文件） | 结构化审计表可查 |
| 处置手段 | 忽略 / 封禁 | 阶梯式处置 |
| 敏感词 | 静态文件 + 重启 | 后台维护 + 热更新 |
| 数据洞察 | 6 个静态数字 | 趋势 + 漏斗 + 导出 |
| 后台形态 | 移动端窄屏 | 宽屏双栏（窄屏自适应） |
| 权限层级 | 超管 = 管理员（空壳） | 超管有独有能力 |
