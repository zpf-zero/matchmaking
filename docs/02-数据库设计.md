# 婚介小程序 · 数据库设计 v2.3（精简版）

> 数据库：`hunjie` · MySQL 5.6+ · `utf8mb4` / `utf8mb4_general_ci` · InnoDB
> 主键统一 `bigint unsigned auto_increment`
> 通用字段：`created_at` / `updated_at` / `deleted_at`（软删，GORM 约定）

**设计原则**：小型项目，够用即可。不做预计算、不做冗余统计表、枚举值放代码不放数据库。

| ban_reason | varchar(255) | 封禁原因 |
| vip_level | tinyint | **权益等级：0 无 / 1 已解锁完整资料（永久）**，默认 0（v2.3 新增） |
| vip_expire_at | datetime | **旧字段，已废弃**（v2.2 引入，v2.3 被 `vip_level` 取代）。保留不删以兼容历史数据与既有代码路径，`json:"-"` 不对外返回 |
| last_active_at | datetime | 活跃时间，推荐流排序依据；鉴权请求最多每 5 分钟刷新一次 |
| created_at / updated_at / deleted_at | datetime | |

> **权益为什么不做独立表**：本项目的权益是「单一维度的解锁状态」，没有任何叠加、降级、套餐差异。一个 tinyint 字段 + 一个 `HasVip()` 方法就够了。做 `vip_user` 表只会让每次查询多一次 JOIN。
>
> **v2.3 为什么从「到期时间」改「永久等级」**：赠送权益用天数没有心理锚点（用户看到「剩 7 天」不知道能换来什么），倒计时还会加速犹豫型用户流失，且续期顺延逻辑是在给一个没有实际价值感的东西做精算。改成永久后，用户不需要理解任何规则，也不会产生「快到期了要不要续」的咨询工单。防刷靠「被邀请人须通过人工审核」这一成本闸门，而不是靠时间衰减。详见 `docs/08-权益体系重构方案.md` 4.4。
>
> 迁移脚本 `migrations/003_benefit.sql` 会把「`vip_expire_at` 未过期」的历史用户批量置为 `vip_level=1`。

> **为什么冗余 `age`**：年龄区间筛选是高频查询，用 `birthday` 做函数计算不利于索引。保存资料时先计算一次，服务启动后由一个 24 小时轻量任务使用 `TIMESTAMPDIFF` 批量修正，不引入任务框架或额外表。

### 原生家庭：默认私有 + 主动授权

`family_*` 六个字段承载最敏感的资料块，双重门禁：

1. **对方主动授权**：`family_visible=1`。默认 0，必须用户自己在资料向导里打开。
2. **我已解锁**：`vip_level >= 1`。

两者同时满足时 `/user/detail` 才返回 `family` 对象。

> **为什么默认私有**：这是敏感度最高的信息，默认公开会劝退大量用户，尤其是一期以体制内为主的用户群。
>
> **为什么「授权了但内容全空」不允许**：保存时若 `hasFamilyContent()` 为 false，服务端强制把 `family_visible` 置 0 —— 否则用户打开授权却什么都没填，别人点进去看到空白，那不叫公开，叫让人白点一下。
>
> **防反查**：父母职业、家庭氛围都用**粗粒度枚举**，不给自由文本填单位；家庭所在地只到城市。写「公务员」可以，写「XX局」不行 —— 后者结合年龄/城市可被反查到具体的人。`family_note` 虽是自由文本，但限 100 字且前端明确提示「请勿填写单位全称、住址等可被反查到的信息」。

## 3.5 three_view_answer 三观问答答案（v2.3 新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint unsigned PK | |
| user_id | bigint unsigned | |
| q_id | smallint | 题目 ID，对应 Go 常量 `ThreeViewQuestions` 的 ID |
| option_idx | tinyint | 所选选项下标 |
| created_at / updated_at | datetime | |

索引：`uk_user_question(user_id, q_id)`、`idx_user(user_id)`

**没有题目表** — 题库定义在 Go 常量 `model.ThreeViewQuestions`（8 道题），与「枚举放代码不放数据库」的既有约定一致。建表等于给自己加一套 CRUD 界面，而题目一年不会改一次。

> ⚠️ **改动题库选项的数量或顺序会让历史答案的 `option_idx` 语义漂移**。若要改，应新增题目（新 ID）而不是修改已有题目的选项。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint unsigned PK | |

## 11. invite_relation 邀请关系与结算

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint unsigned PK | |
| inviter_id | bigint unsigned | 邀请人 |
| invitee_id | bigint unsigned | 被邀请人 |
| code | varchar(12) | 绑定时用的码（留痕） |
| status | tinyint | 0待达成 1已结算 2已作废 |
| settled_at | datetime | 结算时间 |
| created_at | datetime | 绑定时间 |

索引：`uk_invitee(invitee_id)`、`idx_inviter_status(inviter_id, status)`

**状态机**：

```
绑定（注册后提交审核前）────▶ status = 0 待达成
                                   │
                     被邀请人审核通过 ──▶ status = 1 已结算 ──▶ 双方各得权益
                                   │
                       邀请人被永久封禁 ──▶ status = 2 已作废
```

> **`uk_invitee` 唯一索引是防刷的第一道闸**：一个被邀请人只能被绑一次，数据库层面杜绝「一人反复给同一邀请人贡献奖励」。并发重复提交时靠捕获 MySQL 1062 返回幂等结果，不做分布式锁。
>
> **`idx_inviter_status` 支撑两个高频查询**：① 结算时统计 `settled` 数量判断是否封顶；② 计算邀请进度（已结算/待达成）。复合索引而非两个单列索引，因为这两个查询都是「先按邀请人筛、再按状态筛」。
>
> **status = 2 只对未结算的关系生效**。已结算（status=1）的关系即便邀请人后来被封禁也保持原样 —— 封禁只阻止新增，不追回用户已经合法获得的权益。
>
> **为什么绑定和结算要拆成两个状态**：绑定只表示「关系已建立」，此时被邀请人还没填资料、没提交审核，贡献为零。奖励必须等审核通过才发 —— 这既是微信「深度互动」合规要求，也是防刷的成本闸门。

## 核心查询

### 推荐流（最高频）

```sql
SELECT u.id, u.nickname, u.avatar, u.last_active_at,
       p.age, p.height, p.education, p.income_level, p.city, p.marital_status
FROM user u
JOIN user_profile p ON p.user_id = u.id
WHERE u.deleted_at IS NULL
  AND u.status = 2
  AND u.gender = ?                    -- 异性
  AND p.audit_status = 1
  AND p.age BETWEEN ? AND ?           -- 我的择偶要求
  AND p.education >= ?
  AND p.income_level >= ?
  AND p.city_code IN (?)               -- 期望城市，可为空
  AND u.id NOT IN (SELECT to_user_id FROM interaction
                   WHERE from_user_id = ? AND type IN (2,3))
  AND u.id NOT IN (SELECT target_user_id FROM blacklist WHERE user_id = ?)
ORDER BY (u.vip_level >= 1) DESC,
         u.last_active_at DESC
LIMIT 20 OFFSET ?;
```

- `user` 走 `idx_status_gender`，`user_profile` 走 `idx_filter`
- 两个 `NOT IN` 子查询在单用户交互量有限时完全够用
- **不做 rank_score 预计算**。按活跃时间倒序，简单且效果不差
- **权益曝光加成**就是在活跃时间之前插一个布尔表达式：等级 < 1 时表达式自然为 0，不需要额外维护「是否会员」字段。用表达式而非 JOIN 会员表，因为权益等级本来就在 `user` 表上，零额外成本
- `last_active_at` 在鉴权请求中按 5 分钟节流更新，避免频繁写库
- 匹配度百分比在 Go 里算完返回给前端展示，不参与排序
- 前端喜欢用户后重新加载第一页，避免 OFFSET 分页因结果集缩小而漏数据

### 待审核队列

首次审核和复审共用一个队列，但必须排除尚未正式提交的草稿：

```sql
SELECT p.*
FROM user_profile p
JOIN user u ON u.id = p.user_id AND u.deleted_at IS NULL
WHERE p.deleted_at IS NULL
  AND p.audit_status = 0
  AND u.status IN (1, 2)
ORDER BY p.updated_at ASC;
```

- `status=1`：首次提交审核。
- `status=2`：已通过用户修改资料或新增照片后的复审。
- `status=0`：仍是草稿，不进入管理端审核列表。

### 统计数（实时 count，不建统计表）

```sql
-- 谁喜欢我的数量

-- 待审核数量（排除未正式提交的草稿）
SELECT COUNT(*)

JOIN user u ON u.id = p.user_id AND u.deleted_at IS NULL
WHERE p.audit_status = 0 AND p.deleted_at IS NULL AND u.status IN (1, 2);
```

### 「谁看过我」（权益门禁）

```sql
-- ① 总数：口径必须与列表一致，剔除封禁/拉黑/资料下架者
SELECT COUNT(*) FROM user u
JOIN user_profile p ON p.user_id = u.id AND p.audit_status = 1
WHERE u.deleted_at IS NULL AND u.status = 2
  AND u.id IN (SELECT from_user_id FROM interaction
               WHERE to_user_id = ? AND type = 1)
  AND u.id NOT IN (SELECT target_user_id FROM blacklist WHERE user_id = ?);
```

```sql
-- ② 列表：非权益用户只取前 3 条，权益用户取全量
SELECT ... FROM user u JOIN user_profile p ...
ORDER BY i.created_at DESC
LIMIT ? OFFSET ?;   -- 非权益 limit=3；权益 limit=page_size
```

`locked = max(total - free_limit, 0)` 在 Go 里算完返回。

> **总数与列表共用同一个 baseQuery 是硬约束**。如果 `total` 用全表 count、`list` 用过滤后的查询，就会出现「显示锁了 9 条，解锁后只多出 4 条」的幻影 —— 用户会认为权益缩水。对方封禁、拉黑、资料下架后本就不该再计入。
>
> **`page > 1` 时非权益用户直接返回空列表**，否则翻页就能绕过第一页的 3 条限制。门禁做在数据量上而不是接口上，前端不需要为「会员/非会员」写两套调用。
