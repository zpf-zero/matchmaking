# 微信授权登录与分享裂变 · 调研报告

> 日期：2026-10-15
> 范围：① 微信授权登录落地 ② 分享裂变解锁权益的竞品与合规评估
> 结论一句话：**登录只差凭证与两处前端规范化；「分享解锁权益」原样做必违规，需转向「邀请码 + 深度互动结算」。**

## 二、微信授权登录：平台要求与落地方案

### 2.1 能力矩阵（当前有效）

| 能力 | 接口/组件 | 前置条件 | 费用 |
|---|---|---|---|
| 静默登录换 openid | `wx.login` → `code2Session` | 无需授权，无弹窗 | 免费 |
| 手机号一键授权 | `<button open-type="getPhoneNumber">` → 后端 `getuserphonenumber` | **企业主体 + 微信认证**；后台完成隐私指引 | **0.03 元/次**，每小程序 1000 次免费额度 |
| 头像 | `<button open-type="chooseAvatar">` → `e.detail.avatarUrl` | 无 | 免费 |
| 昵称 | `<input type="nickname">` → 键盘顶部提供微信昵称建议 | 无 | 免费 |
| 内容安全 | `msg_sec_check` | 企业主体 | 免费 |

### 2.2 必须知道的两次平台变更

**变更一：`getUserProfile` / `getUserInfo` 已回收头像昵称**

自基础库 2.27.1 起，`wx.getUserProfile` 不再返回真实头像昵称，也不弹授权窗，统一返回灰色头像 + 「微信用户」。**不要再把它当主路径**。

正确做法（「用户自主时代」）：
- 头像 → `<button open-type="chooseAvatar" bind:chooseavatar="onChooseAvatar">`
- 昵称 → `<input type="nickname" bindchange="onNick">`

> 注意：`chooseAvatar` 给到的是**临时文件路径**，必须上传到自己服务器持久化 —— 这正好套用项目已有的 `POST /common/upload/image`。

**变更二：分享回调已被砍掉**

自 2024-07-05 新提交版本起：
- 小程序分享给好友后，**开发者无法获知用户是否分享完成**（`success`/`cancel` 统一为 `success`）
- 分享到群后**不再立即返回 `shareTicket` / 群 ID**（但卡片被群成员打开时仍可拿到）

**这条变更对本次调研意义重大**：它意味着「检测到分享成功 → 发奖励」这条技术路线**已经死了**。任何裂变结算都只能基于「分享卡片被打开 + 打开者完成真实业务行为」，而这恰好**天然满足微信要求的「深度互动」**。合规与可行在此处是同一个方向。

### 2.3 落地改动清单

**后端**（改动很小）

| 文件 | 改动 |
|---|---|
| `config.prod.yaml` | 填 `app_id` / `app_secret`，`mock: false` |
| `wechat.go` | 无需改动，`realClient` 已实现完整 |
| `service/auth.go` | 无需改动 |
| `handler/common.go` | 可选：`ClientConfig` 增加 `need_privacy_agreement` 等开关 |

**前端**（主要工作量）

| 文件 | 改动 |
|---|---|
| `pages/profile/setup.vue` | 头像改 `chooseAvatar` 按钮；昵称 input 加 `type="nickname"` |
| 手机号步骤 | 替换为 `<button open-type="getPhoneNumber" @getphonenumber>`，取 `e.detail.code` 提交 `/auth/bind-phone` |
| `manifest.json` | 填 `appid` |
| 全局 | 接入 `wx.onNeedPrivacyAuthorization` / `wx.requirePrivacyAuthorize` 处理隐私弹窗 |
| `pages/login/index.vue` | 保留 Mock 分支用于开发，真实分支逻辑已可用 |

**小程序后台**（人工，不可跳过）

1. 完成**微信认证**（企业/个体工商户主体）
2. 配置**《用户隐私保护指引》**：明确声明收集手机号、头像、昵称，用途写清楚
3. 类目选择「社交 - 婚恋交友」，上传资质
4. 「付费管理」确认手机号验证服务额度

### 2.4 成本与风险

| 项 | 说明 |
|---|---|
| 手机号组件费用 | 0.03 元/次，1000 次免费。1 万新用户 ≈ 270 元 |
| 认证费 | 300 元/年（微信官方） |
| 最大风险 | **类目资质**。见 2.5 |

### 2.5 类目资质：真正的拦路虎

「社交 - 婚恋交友」类目要求 **《增值电信业务经营许可证》（ICP 经营许可）**，办理条件苛刻：

- 注册资本 ≥ 100 万
- 3 名员工近 3 个月社保
- 服务器在境内

**实测可行的替代路径**：向当地通信管理局提交申请，拿到 **《行政许可不予受理通知书》** 后，在微信后台作为资质材料提交，可通过内容主管部门的二次审核。这是小团队的低成本合规通道。

> 这条决定了「什么时候能真机跑通真实登录」—— 不是技术问题，是资质问题。

## 三、竞品调研

### 3.1 头部产品权益设计对比

| 产品 | 付费/权益载体 | 核心权益点 | 拉新玩法 |
|---|---|---|---|
| **珍爱网** | 超级会员（月度/年度）、珍爱币 | 超级推荐（推荐页加权曝光）、超级提醒（置顶）、**隐身访问**、查看谁看过我、畅聊次数、资料页装扮、直播间装扮 | 未见强分享裂变，以**线下红娘 + VIP 托管**为高价变现 |
| **珍爱网（星级特权）** | 星级特权 | **搜索排名优先**、查看对方最后登录时间、**查看谁关注了我**、查看距离 | — |
| **世纪佳缘** | 会员约 249 元 | 消息自动解锁、**谁看过我**、**谁中意我**、谁有车有房、更多筛选条件 | — |
| **网易花田** | 高级 VIP | 与推荐对象聊天权限 | — |
| **伊对** | 积分、虚拟礼物、红娘分佣 | 视频相亲、直播间守护 | 邀请好友注册并完成**实名认证** → 双方得积分/现金；**红娘撮合成交拿佣金**；社群裂变（群达人数群主得奖励） |
| **比心单身**（校园） | 桃花券 | — | 转发后**新用户点击**即送桃花券 |
| **分配对象**（校园） | — | 分享可解锁「心动我的」 | 72 小时 CP 活动、分享拉新提高匹配成功率；病毒系数 1.82 |

**读出来的规律**：

1. **头部严肃婚恋几乎不做分享裂变**。珍爱、佳缘、花田的变现全部压在「会员订阅 + 红娘服务」上，裂变靠的是**线下活动和公众号内容**，不是小程序分享。
2. **权益设计的共同锚点是「信息可见性」** —— 谁看过我、谁关注我、最后登录时间、距离。这些都是**把「别人对我的行为」卖给你**，成本为零、用户感知强烈。
3. **做分享裂变的是校园/轻社交产品**（比心、分配对象），不是严肃婚恋。
4. **伊对的红娘分佣是最稳的裂变模型** —— 把拉新收益给到「有动机的人」（红娘），而不是「有社交压力的人」（普通用户）。

### 3.2 关键洞察：婚恋品类的「分享悖论」

这是本次调研最重要的商业判断：

> **严肃婚恋用户主动把小程序分享给微信好友，存在天然心理障碍。**

原因：
- 分享到好友/群 = 向熟人圈子**公开自己正在相亲**，且暴露择偶条件（学历、收入、婚房）
- 目标用户 22-45 岁、有明确结婚意愿，**社交形象敏感度远高于校园用户**
- 分享卡片的标题、配图必然带婚恋属性，无法「假装是别的东西」

**推论**：
- 用「分享解锁权益」硬拉，**转化率会显著低于社交/工具类产品**
- 更要命的是，它同时踩中**合规红线**（见第四章）
- 所以正确方向不是「想办法让人分享」，而是**换一条不依赖用户社交勇气的拉新路径**

### 3.3 三条可选路径

| 路径 | 说明 | 适配度 |
|---|---|---|
| A. 邀请码（隐形裂变） | 由「被邀请者主动填码」或「线下/社群发码」完成，不必暴露给熟人圈 | ⭐⭐⭐⭐⭐ |
| B. 红娘分佣 | 招募兼职红娘，按其拉新+撮合成果结算 | ⭐⭐⭐⭐ |
| C. 自然分享（内容型） | 分享「脱单攻略」「匹配度测试」等无压力内容 | ⭐⭐⭐ |
| D. 强制分享解锁 | ❌ 违规 | — |

## 四、合规红线：为什么「分享解锁权益」不能直接做

### 4.1 《微信小程序平台运营规范》5.1 九条

| 条款 | 内容 |
|---|---|
| 5.1.1 | **强制用户分享**：分享后才能继续下一步，**如分享后才能解锁功能**、分享后才能查阅/下载图片或视频 |
| 5.1.2 | **暗示用户分享**：红点提醒分享、分享按钮动态变化 |
| 5.1.3 | **诱导分享朋友圈**：诱导分享至朋友圈获取利益 |
| 5.1.4 | **无深度互动诱导分享**：以分享后无需互动或无需深度互动即获利益的方式诱导分享至群或好友 |
| 5.1.5 | 分享活动误导用户（规则不明确、标题党、信息不显著） |
| 5.1.6 | 分享收益存在概率性（抽奖式诱导） |
| 5.1.7 | 分享收益非即时获得（要求长期参与才给） |
| 5.1.8 | **组队组团类分享活动参与总人数未限制在 5 人内** |
| 5.1.9 | 过度营销分享（分享量过大且转化率过低，会被自动限制分享能力） |

其中「利益」的定义极宽：**现金奖励、实物奖品、虚拟奖品（红包、优惠券、代金券、积分、话费、流量、信息等）**。会员权益、曝光加成、额外匹配次数，全部落在「虚拟奖品」里。

### 4.2 逐条对照「分享裂变解锁权益」

| 设想中的做法 | 命中条款 | 判定 |
|---|---|---|
| 分享给 1 位好友，解锁「查看谁看过我」 | 5.1.1 | 🔴 违规（规范原文举例就是「分享后才能解锁功能」） |
| 分享到群，得 1 次高级匹配 | 5.1.4 | 🔴 违规（被分享者无需深度互动） |
| 在分享按钮上加红点提示可领奖 | 5.1.2 | 🔴 违规 |
| 分享到朋友圈得会员天数 | 5.1.3 | 🔴 违规（朋友圈尤其敏感） |
| 邀请 3 人组队，满员解锁 | 5.1.8 | 🟡 若总人数 >5 违规 |
| 邀请满 10 人，抽 1 人送会员 | 5.1.6 | 🔴 违规（概率性收益） |
| 连续邀请 7 天才能领奖 | 5.1.7 | 🔴 违规（非即时） |
| **邀请新用户注册并完成资料审核，双方各得 7 天会员** | — | 🟢 **不违规**（深度互动 + 即时 + 规则明确） |
| **用户主动填写邀请码，自己得权益** | — | 🟢 不违规（非分享行为） |

### 4.3 处罚等级

| 情节 | 处置 |
|---|---|
| 轻 | 阶梯封禁**分享能力** |
| 中 | 封禁**朋友圈二维码识别能力** |
| 重 | 限制活动页面功能、**下架封号** |

微信还会对「同一主体下小程序分享量大但转化率低」的行为**自动限制分享能力**（5.1.9）。这个判定是自动的，不需要人工举报。

### 4.4 关键区分：什么是「深度互动」

规范的原文定义：

> 「深度互动」是指被分享者**理解被分享内容并主动参与活动或业务流程**，从而执行的**进入页面、点击等一系列相关操作**。

对照本项目，**「新用户注册 + 完善资料 + 通过人工审核」是教科书级的深度互动** —— 它不是点一下就走，而是一段有真实成本的业务流程。这为第五章的方案提供了合规基础。

> 注意一条实践提醒：微信社区里的共识是「是否符合规范」在有争议地带会依赖审核员人工判断。因此方案设计应**留足余量**，不要把「擦边合规」当设计目标。

## 五、方案评估：三个可选设计

### 5.1 方案 A：邀请码 + 深度互动结算（推荐）

**核心机制**

```
老用户 A 获得专属邀请码（如 6 位短码 / 小程序码）
       ↓
新用户 B 通过以下任一方式进入并填码：
  ① 线下/社群/朋友圈发码（不暴露给熟人）
  ② 扫码进入（scene 带参，自动识别）
  ③ 注册流程中手填邀请码
       ↓
B 完成注册 → 完善资料 → 通过人工审核  ← 深度互动达成
       ↓
双方各得权益：B 得新人福利，A 得邀请奖励
```

**为什么不违规**

| 检查项 | 本方案 |
|---|---|
| 是否有「不分享就不能用」 | ❌ 否。全部功能不分享也能用 |
| 是否依赖「分享成功回调」 | ❌ 否。微信已砍掉该回调，本方案基于被邀请人完成任务 |
| 被邀请者是否深度互动 | ✅ 注册 + 填资料 + 通过审核 |
| 收益是否即时 | ✅ 审核通过即到账 |
| 收益是否概率性 | ❌ 否，固定额度 |
| 组队人数 | 单次邀请关系是 1v1，不涉及组队 |
| 活动规则是否显著告知 | 需在页面明确规则（必做项） |

**权益设计**（沿用竞品的「信息可见性」锚点）

| 权益 | 说明 | 对标 |
|---|---|---|
| 「谁看过我」完整列表 | 免费版只看最近 3 条且模糊，权益版全量 | 世纪佳缘、珍爱 |
| 推荐曝光加成 | 7 天内推荐流排序加权 | 珍爱网「超级推荐」 |
| 每日额外推荐额度 | 免费 3 次 → 权益 9 次 | 通用 |
| 隐身访问 | 看别人不留下痕迹 | 珍爱网超级会员 |

**优先级建议**：一期只做「谁看过我」+「曝光加成」两项，其余二期。

### 5.2 方案 B：红娘分佣（拉新效率最高）

**机制**：招募兼职红娘（可以是活跃用户、线下婚介从业者），发放专属邀请码/小程序码，按「被邀请人通过审核」计件结算，按「成功撮合配对」额外分成。

**优点**
- 拉新动机来自**利益**而非**社交勇气**，绕开了 3.2 的分享悖论
- 邀请码可线下发放，完全不依赖微信内分享
- 伊对已验证的模式

**缺点**
- 涉及**分佣结算**，需要提现/账务能力，项目一期「不接微信支付」，落地成本高
- 需要防刷（红娘批量注册假号），风控复杂度上升
- 若走现金分佣，可能触及「分销」合规边界

**建议**：**二期**做，且优先用「权益兑换」而非现金分佣，规避支付与分销风险。

### 5.3 方案 C：内容型自然分享

**机制**：分享的不是「相亲邀请」，而是无社交压力的内容，例如「测一测你的择偶匹配度」「脱单避坑指南」。用户分享的是「一个有意思的测试」，不是「我在相亲」。

**优点**
- 绕开分享悖论
- 不带利益诱导，合规最干净（不触发 5.1 任何一条）

**缺点**
- 需要内容运营能力，是**长期活**，不是一次性功能
- 转化链路长（内容 → 小程序 → 注册 → 通过审核）

### 5.4 三方案对比

| 维度 | A 邀请码 | B 红娘分佣 | C 内容分享 |
|---|---|---|---|
| 合规风险 | 🟢 低 | 🟡 中（视结算方式） | 🟢 最低 |
| 对分享悖论的规避 | ✅ 好（码可线下发） | ✅ 最好 | ✅ 好 |
| 拉新效率 | 中 | **高** | 中低（但长尾） |
| 开发成本 | 中 | 高 | 低（功能）／高（运营） |
| 依赖支付能力 | 否 | **是** | 否 |
| 一期可落地 | ✅ **是** | ❌ 二期 | ✅ 可并行 |

**推荐组合**：**一期做 A，同步试水 C；B 放二期。**

## 六、方案 A 详细设计

### 6.1 数据模型（保持小项目风格，只加 2 张表 + 1 个字段）

**改 1 处：`user` 表加权益字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `vip_expire_at` | datetime NULL | 权益到期时间。NULL = 无权益。判定 `vip_expire_at > now()` 即生效 |

> 一期用「到期时间」而非独立会员表，避免引入订单/续费/退款一整套。二期接支付时再演进为 `user_membership`。

**新增表 1：`invite_code` 邀请码**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| user_id | bigint | 归属用户（唯一） |
| code | varchar(12) | 短码，唯一索引。**必须短**（小程序码 scene 上限 32 字符） |
| created_at | datetime | |

**新增表 2：`invite_relation` 邀请关系与结算**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| inviter_id | bigint | 邀请人 |
| invitee_id | bigint | 被邀请人，**唯一索引**（一人只能被邀请一次，防刷） |
| code | varchar(12) | 使用的邀请码 |
| status | tinyint | 0 待达成 / 1 已结算 / 2 已作废 |
| settled_at | datetime NULL | 结算时间 |
| created_at | datetime | |

**设计要点**
- `invitee_id` 加**唯一索引**，从数据库层面杜绝「同一个人被多次邀请刷奖励」
- 关系**绑定在注册时**，**结算在资料审核通过时** —— 绑定与结算分离，是这套方案合规的核心
- 不在 `user` 表加 `inviter_id`，因为奖励需要流水记录，独立表便于对账

### 6.2 接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/v1/invite/my-code` | Auth | 取（或惰性生成）我的邀请码 + 已邀请人数 + 已得权益 |
| POST | `/api/v1/invite/bind` | Auth | 提交邀请码绑定关系。校验：码存在、不是自己、自己未被邀请过 |
| GET | `/api/v1/invite/records` | Auth | 我的邀请记录（被邀请人昵称脱敏 + 状态） |

**不新增「分享成功上报」接口** —— 因为微信已无法返回分享结果，上报毫无可信度。

**权益判定**：在 `middleware` 或 service 层加一个轻量 `HasVip(u)` 判断，不加中间件（避免每条路由都挂）。

### 6.3 结算时机（关键）

```
B 注册           → 写入 invite_relation，status=0（待达成）
B 提交资料       → 无变化（此时是「待审核」，仍有反悔/被拒可能）
B 审核通过       → status=1，发放双方权益
```

**为什么必须等到「审核通过」**
1. 这是「深度互动」的最强证明 —— 审核通过意味着 B 是真实、完整、合规的用户
2. 空号/资料不全的号拿不到奖励，天然对抗刷量
3. 结算时机越靠后，薅羊毛的成本越高

**风控补充**
- 同一设备/同一手机号多次注册 → 只结算首次
- 邀请人自身必须 `status=2`（正常），封禁/未完善用户不参与
- 单账号邀请奖励**封顶**（如最多结算 20 人），防止红娘化刷量

## 八、风险与未决项

| # | 项 | 说明 | 处理 |

| R1 | 类目资质 | 无 ICP 许可则无法过审，是**上线最大阻塞** | 优先申请「不予受理通知书」替代路径 |
